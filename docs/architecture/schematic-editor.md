## 1. Current implementation

- `view/drawing.py` (`DrawingView`) draws onto a `Gtk.DrawingArea` with Cairo:
  background grid, template border, title block, elements, selection, floating
  insert model and wire preview. A cached background surface speeds redraws.
- Interaction modes: default, box selection, insert (floating model with
  rotate `R` and port cycling `C`), add wire (click points, finish on
  double/middle click or on a port, cancel with right click or Escape).
- Each element draws itself from `schem_model` (primitives in grid units) and
  `text_model` (`${...}` label templates over field values, evaluated by the safe expression evaluator since M3; Mako before). Orientation is a 90°
  rotation; there is no mirroring or free rotation.
- Connectivity is computed later by `NetworkModel` from coincident port
  coordinates; the editor does not maintain connection records.
- The same Cairo code produces drawing PDFs and prints.

## 2. Principles for the new editor

1. **Canonical data stays in Python.** Elements, wires, positions, orientation,
   fields, sheets and connectivity rules live in the backend document. The
   frontend library holds a disposable view model rebuilt from backend state.
2. **Connectivity semantics do not change.** Ports connect when coordinates
   coincide on a sheet; references connect across sheets by `ref`. The frontend
   may *display* derived connections (junction dots, highlighted nets) computed
   by the backend; it never decides them.
3. **Edits are commands.** Pointer interactions produce commands
   (`drawing.insert`, `drawing.move`, `drawing.add_wire`, `drawing.edit_wire`,
   `drawing.rotate`, ...). The backend snaps, validates, applies, records undo
   and returns authoritative geometry plus connectivity changes.
4. **No library undo.** The library's own undo manager is disabled; undo/redo
   goes through the backend history.
5. **Exact coordinates.** Committed coordinates are integers in drawing units;
   the adapter rounds library floats before sending and never writes back
   rounded-off values without a command.
6. **Labels are computed in Python.** The backend sends rendered label lines
   for each element; the frontend only lays them out. This retires Mako on the
   rendering path without duplicating formatting rules in TypeScript.

## 3. Symbol pipeline

| Step | Output | Notes |
| --- | --- | --- |
| Convert `schem_model` → SVG (one-off tool, then maintained) | `gelectrical/symbols/svg/<code>.svg` | Primitive mapping: `LINE`→`<line>`, `CURVE`→cubic `<path>`, `ARC`→arc `<path>`, `CIRCLE`→`<circle>`, `RECT`→`<rect>`, `PATH`→`<path>`; dash arrays and the four stroke widths become classes |
| Port and anchor metadata | `<circle class="eui-port" data-port="0" cx cy r="0"/>` + `data-anchor` | Ports in drawing units relative to the element origin; editable in Inkscape (object properties/XML editor) |
| Parameterised symbols | `gelectrical/symbols/definitions/<code>.json` | For busbar width, reference box width, transformer variants, display text box: parameters → primitive list generated by Python |
| Text slots | `data-label-slot` positions | Label lines come from the backend |
| Sprite for the frontend | generated `symbols.svg` sprite or per-symbol strings | Built from the same files; no hand-copied paths in TypeScript |
| PDF output | Cairo renderer in `gelectrical/symbols/render_cairo.py` | Consumes the same definitions; replaces per-element `render_element` |

Static symbols are edited in Inkscape (plain SVG, no Inkscape-only features
required). A validation script checks that each symbol's ports match the element
class `ports` exactly; mismatches fail the build. During migration, a parity test
renders each element with the legacy `render_element` and the new renderer to
PNG and compares within a pixel tolerance.

Automatic conversion is expected to cover all current primitives, because
`schem_model` is already declarative data. Elements that build `schem_model`
dynamically in `render_element` (for example busbar, reference box, switches
with state, display text) become parameterised definitions.

## 4. Requirements and evaluation

Both candidates render SVG in the webview. "maxGraph" means `@maxgraph/core`
(Apache-2.0, TypeScript successor of mxGraph). "Custom SVG" means Vue-rendered
SVG with EngineeringUI `drawing/` utilities (viewport, grid, snapping,
selection), optionally using SVG.js (MIT) for DOM manipulation.

| Requirement | GElectrical need | maxGraph (to verify) | Custom SVG |
| --- | --- | --- | --- |
| Custom electrical symbols | ~35 element types | Stencils or SVG image shapes; custom `Shape` classes | Direct `<use>`/inline SVG |
| SVG symbol definitions | Inkscape-editable | SVG as image shape loses per-element styling; stencil XML is a separate format | Native |
| Dynamic/parameterised symbols | Busbar width, ref box, switch state | Custom shape classes | Re-render from backend primitives |
| Connection ports | Port metadata per symbol | Connection constraints or port child cells | Port markers + hit areas |
| Adjustable busbars | Width changes ports | Custom resize handler + recompute ports | Custom handle |
| Orthogonal and manual wires | Polylines with grid points; free routing | Edge styles (`OrthConnector`, segment edges), waypoints | Polyline editing handles |
| Junctions and branches | Coordinate coincidence, T-junctions | Edges terminate on cells; dangling terminal points possible; junctions need extra vertices | Junction dots from backend net data |
| Grid snapping | 16-unit grid, 8-unit ports | Built-in grid | Utility in `drawing/` |
| Precise coordinates | Integer drawing units | Float geometry; adapter rounding | Full control |
| Rotation | 90° orientation today | Style rotation | Transform attribute |
| Selection, box select, toggle | Required | Built in (rubberband) | Utility |
| Grouping and assemblies | Assembly boxes | Groups (cells with children) | Overlay rectangles |
| Copy/paste | Backend payload | Backend payload either way | Backend payload |
| Undo/redo | Backend history | Disable library undo | Backend history |
| Multiple sheets | One canvas per sheet | One graph model per sheet | One component per sheet |
| Border and title block | Must match PDF | Background image/layer | Backend-generated SVG layer |
| Dynamic labels | Backend label lines | Cell labels / HTML labels | `<text>` elements |
| Analysis overlays | Node results, loading colours, markers | Overlays or extra cells | Overlay layer |
| Zoom and pan | Required | Built in | Utility |
| Large schematic performance | Target below | Proven at scale in diagram apps | Must be measured |
| Vector PDF | Cairo backend (unchanged) | Not used for PDF | Not used for PDF |
| High-DPI / fractional scaling | Required | SVG | SVG |

### Selection criteria (decision gate for M7)

| # | Criterion | Weight | Pass condition |
| --- | --- | --- | --- |
| 1 | Connectivity fidelity | must | Backend connectivity after PoC edits equals the legacy engine for all sample projects |
| 2 | Coordinate fidelity | must | Load → display → save without edits is byte-identical in canonical JSON |
| 3 | Symbol fidelity | must | All element types render; PNG diff with legacy within tolerance |
| 4 | Interaction completeness | high | Insert, rotate, port cycle, wire draw/edit, junctions, select/box/toggle, move, delete, assemblies, zoom/pan, keyboard shortcuts |
| 5 | Performance | high | 1,000 elements + 2,000 wire segments on one sheet: pan/zoom frame under 16 ms median, selection update under 100 ms, initial load under 1 s on a mid-range laptop |
| 6 | Code size and clarity | medium | Adapter code that a contributor can follow; no fighting the library's model |
| 7 | Accessibility | medium | Keyboard selection and movement; screen-reader names for elements |
| 8 | Maintenance and licence | must | Active releases, Apache-2.0/MIT, no proprietary add-ons |
| 9 | Bundle size | low | Measured and recorded |

Choose maxGraph if it passes all *must* criteria and is not worse on criteria
4–6. Otherwise choose custom SVG. Record the measurements and the decision in
ADR 0005. Main known risk for maxGraph: its edge-to-terminal connection model
differs from coordinate-coincidence connectivity, so the adapter may need to
suppress most of maxGraph's connection logic.

## 5. Editing behaviour notes

- **Moving elements:** today a drag moves a single element by deleting it and
  re-inserting it at the end of the element list (its positional identity
  changes); wires are not dragged along, so connections break if wire endpoints
  no longer coincide. Parity keeps the connectivity behaviour; stable `uid`s
  remove the identity change. Parity comes first (owner decision Q6); moving
  multiple selected elements is an enhancement after M15 or behind an option. A "keep
  connections" option (backend adjusts attached wire endpoints in the same
  command, with preview) is an enhancement and must be listed as `Changed`.
- **Automatic routing and snapping** must never create or break connections
  silently. The backend returns connectivity deltas (`joined`, `split`
  node sets); the editor shows them, and MCP responses report them.
- **Display nodes:** analysis node markers become an overlay, not document
  elements ([backend](backend.md#6-analysis-jobs)).

## 6. Proof of concept scope (M7)

1. Symbol converter: generate SVG for every registered element from
   `schem_model`; port metadata; validation script.
2. Load `sample.gepro` through a fixture JSON export (no live backend required
   initially), render both sheets with border and title block.
3. Implement insert, move, rotate, wire drawing with junctions, box selection
   and zoom/pan in both candidates on the same fixture.
4. Send edits to a stub command recorder; replay them through the Python engine
   in a test and compare connectivity with the legacy result.
5. Generate a 1,000-element synthetic sheet; measure criteria 5.
6. Write ADR 0005 with results.
